# ADR-003: Splitter Authentication Model

## Status
Accepted

## Context
Splitters create bills, review OCR outputs, manage participants, finalize splits, and track participant payment statuses. They require authentic access to their bill history across sessions.

## Decision
Splitter authentication will be based on:
```text
Phone Number -> OTP Verification -> JWT Issuance
```

1. **Phone Normalization**: Phone numbers normalized to E.164 format (e.g. `+919876543210`).
2. **OTP Flow**: Splitter requests OTP -> system generates secure 6-digit OTP -> SMS delivered (or dev provider) -> Splitter posts OTP -> backend validates -> JWT issued.
3. **JWT Scope**: Contains Splitter ID (`sub`), role (`Splitter`), and token expiration claims.
4. **Access Rights**: Splitters are authorized to view full bill details, participant lists, payment states, and historical bills owned by them.

## Consequences
- **Positive**: Low-friction login, no password management/reset burden, secure JWT authorization.
- **Negative**: SMS delivery dependency in production.
- **Mitigation**: Abstracted SMS provider (`ISmsProvider`) with a zero-cost local Development SMS Provider.
