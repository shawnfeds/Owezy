# ADR-008: Monetary Precision & Rounding Algorithm

## Status
Accepted

## Context
When splitting bills among multiple participants, fractional cents/paisa often arise (e.g. ₹100 split 3 ways yields ₹33.3333... per person). Floating-point arithmetic causes precision loss and non-deterministic rounding errors. The sum of all participant totals must reconcile exactly to the bill total.

## Decision
1. **Data Type**: All monetary representations in domain models, entities, DTOs, and calculations MUST strictly use C# `decimal` and SQL `decimal(18,2)`. Floating-point types (`float`, `double`) are strictly forbidden.
2. **Authoritative Rounding Algorithm**: **Largest Remainder Method (Hare-Niemeyer Method)**:
   - Calculate unrounded fractional shares for each participant.
   - Floor each share to the smallest monetary unit (2 decimal places / paisa).
   - Calculate remaining unallocated units (`BillTotal - Sum(FlooredShares)`).
   - Rank participants by their fractional remainder (`ExactShare - FlooredShare`) descending.
   - Distribute 1 extra monetary unit (₹0.01) to participants with the largest remainders until remaining units are zero.
3. **Deterministic Tie-Breaking**: When remainders are equal, break ties using deterministic ordering (Participant Creation Timestamp ascending, followed by Participant ID ascending).
4. **Rejection of Disallowed Schemes**: "Give leftover cents to bill owner" or arbitrary floating-point rounding schemes are strictly prohibited.

## Consequences
- **Positive**: Guaranteed exact financial reconciliation (`Sum(ParticipantTotals) == BillTotal`), 100% deterministic results across all platforms.
- **Negative**: Requires careful implementation and thorough unit testing for edge cases.
- **Mitigation**: Dedicated domain engine class (`LargestRemainderSplitter`) covered by extensive unit tests in `Owezy.UnitTests`.
