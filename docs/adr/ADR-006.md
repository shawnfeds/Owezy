# ADR-006: OCR Abstraction & Cost Control Strategy

## Status
Accepted

## Context
OCR scanning speeds up receipt entry, but cloud OCR APIs incur monetary costs per API call. Repeated scans of identical receipts, retries, or unthrottled requests can rapidly consume budgets. Additionally, OCR is advisory—the Splitter's manual review is authoritative.

## Decision
1. **Application Interface**: OCR must be hidden behind an `IOcrService` interface in `Owezy.Application`, decoupling domain logic from external OCR provider implementation details.
2. **Image Hashing & Deduplication**: Compute SHA-256 hash of incoming receipt images prior to sending external OCR requests.
3. **Caching**: Store OCR analysis results indexed by SHA-256 image hash in SQL Server / local cache. If an identical hash is submitted, return cached OCR results without making an external OCR API call.
4. **Architecture Resilience Requirements**:
   - Retry handling for transient failures
   - Rate limiting on upload endpoints
   - Circuit breaking where justified
   - Cost protection and controlled external requests
   - Appropriate resilience library/pattern selected during Phase 3 implementation
5. **Advisory Nature**: OCR results populate candidate items (`Name`, `Quantity`, `UnitPrice`, `LineTotal`). The user review step is required to finalize the bill.

## Consequences
- **Positive**: Low cloud OCR cost, resilience against duplicate uploads, protection against API rate limits and failures.
- **Negative**: SHA-256 caching requires identical image binary streams; slight image cropping/rotation produces distinct hashes.
- **Mitigation**: Acceptable for v1; avoids complex computer vision deduplication while keeping infrastructure lightweight.
