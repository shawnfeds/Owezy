# ADR-002: Architectural Pattern — Modular Monolith

## Status
Accepted

## Context
Owezy is a lightweight, scope-controlled application. Microservices, event buses, and distributed systems introduce unnecessary operational complexity, network latency, deployment overhead, and failure modes that violate v1 design principles.

## Decision
Adopt a **Modular Monolith** structure within a single .NET 10 solution (`Owezy.slnx`).

### Project Layout
- `Owezy.Api`: Web API entry point, controllers, HTTP middleware, routing, rate limiting.
- `Owezy.Application`: Business use cases, DTOs, interfaces, and module logic (`Auth`, `Billing`, `OCR`, `Splitting`, `Payments`, `Sharing`).
- `Owezy.Domain`: Core domain entities, value objects, domain exceptions, and calculation logic.
- `Owezy.Infrastructure`: EF Core DbContext, repository implementations, Azure OCR provider, SMS providers, security token generation.
- `Owezy.Client`: Single-page client application (PWA/UI).

### Unit & Integration Test Suites
- `Owezy.UnitTests`: Domain and Application unit tests.
- `Owezy.IntegrationTests`: End-to-end API and database integration tests.
- `Owezy.ArchitectureTests`: NetArchTest rules enforcing strict directional layer boundaries (`Domain` $\leftarrow$ `Application` $\leftarrow$ `Infrastructure` $\leftarrow$ `Api`).

## Consequences
- **Positive**: High maintainability, zero network overhead between business modules, simplified local debugging, easy deployment.
- **Negative**: Requires strict module boundary discipline to prevent monolithic complexity.
- **Mitigation**: Automated architecture tests (`Owezy.ArchitectureTests`) will fail the build if modules or layers cross boundaries improperly.
